# RN and Flutter foundational capability audit

Neon has most of the familiar building-block families, but not their complete contracts. The largest gaps are input/activation safety, focus and accessibility, editing semantics, portable typography, image loading and a few accepted-but-unimplemented behaviors. Adding more named widgets would not close these gaps.

This is a read-only implementation audit dated 2026-10-15, not an implementation plan, release gate or claim that every prop was enumerated. No builds, tests, devices or assistive technologies were driven. Source findings below are not runtime reproductions.

## Scope and reference boundary

- **Primitive:** foundational animation, geometry, input, scheduling, environment and system-service mechanisms.
- **Primitive-component:** a minimal neutral building block such as View, Text, TextInput, Image, Pressable or a scrolling container. Equivalent style/composition counts; a missing Flutter class name alone does not count.
- **Excluded:** Picker, Toast and other concrete styled/product UI; Tooltip, popover, dropdown and positioning/follow-anchor engines, even unstyled; navigation implementation. Existing widgets are not removed or relocated.
- **Architecture retained:** RN-shaped author contracts, Solid ownership/reactivity, one NeonNode, native Yoga/views and browser DOM/CSS. Flutter is capability/reference evidence, not permission to import its rebuild model, engine or render-sliver protocol.

## Security and activation findings

### S1 — accepted secure input can paint clear text

Source trace, not a runtime disclosure reproduction:

- `src/components/primitives.ms` TextInput accepts `secureTextEntry` and chooses the multiline host tag independently, without rejecting their combination.
- `src/platform/void/host.ms` `setAttr` handles style/value, not secure entry; `showField` assigns `TextEditingValue.text` directly to the drawn label. The Void host is already parked on API drift, so this is also a latent risk when that host becomes runnable again, not proof of a currently running Void app.
- `src/platform/browser/dom.ms` creates a `textarea` for multiline input; its secure-entry handler only sets `type=password`. That does not mask a textarea. The inspected textarea stylesheet adds no masking mechanism.
- `F/src/widgets/editable_text.dart` EditableText constructor, around line 962, asserts that obscured fields cannot be multiline. That is reference contract evidence, not proof of release-mode rejection or a mandate to copy an assertion.

Do not advertise these paths as secure fields. A future fix must prove either real obscuring or explicit rejection before painting, including supported/unsupported host and multiline variants. No fix or runtime pin is supplied by this audit.

### S2 — activation is not equivalent across input paths

- **Browser:** Pressable with press-in/out/long-press opts into pointer handlers and registers no `onPress` click handler; the final press occurs inside pointer-up. `src/render/node.ms` maps it to a button, whose keyboard activation produces a click rather than that pointer route. See Pressable in `src/components/primitives.ms` and event routing in `src/platform/browser/dom.ms`. This is a source-confirmed missing activation path; keyboard/AT execution was not driven.
- **Native:** public key handlers are accepted, but `src/platform/native/contract.ms` `createNativeEventRegistry` has no key-producing dispatch/control phase. Input controls still produce text/selection/submit events; that is not generic hardware-key delivery.
- **Assistive technology:** custom Pressable paths are touch-driven. No explicit custom activation/action callback bridge was found in the inspected UIKit/Android custom-view paths. Built-in controls and platform default behavior still matter; this is not a measured claim that every VoiceOver/TalkBack activation fails.

Reference: `RN/Libraries/Components/Pressable/Pressable.d.ts`; `F/src/widgets/gesture_detector.dart` semantic tap integration; `F/src/widgets/keyboard_listener.dart` KeyboardListener. Regression proof must include keyboard/semantic activation, not only synthetic pointer input.

## Host distinctions and excluded catalog names

- **Browser:** real DOM/CSS implementation and useful native browser behavior; not a blanket fallback that makes ignored props portable. Source gaps above distinguish CSS selection, button defaults and browser-only escapes from shared APIs.
- **iOS:** substantial real UIKit/native Yoga paths; normal input, modal layers and platform semantics do not prove every custom-key/action/text prop. This audit ran neither simulator nor physical proof.
- **Android:** real source paths, but the previous installed-toolchain measurement consumer was compiler-C-string-blocked. No Android runtime certificate follows from Java/JNI source.
- **Void:** drawing/editing/key/preedit infrastructure exists, but the current Neon host is parked on NodeRef API drift. It also ignores many shared attrs and lacks scrolling/overlay/measurement capability hooks. S1 must not be lost when the host is restored.
- **Terminal:** boxes/text and stored event routes are not native text editing, scrolling, image or accessibility parity. Explicitly unsupported capabilities must stay explicit.
- **Button:** styled/platform-opinionated composition, not an additional mandatory neutral primitive; Pressable+Text is the underlying building ability.
- **Switch/ActivityIndicator:** useful borderline native input/display controls already exist. Their field/value-domain differences are not proof of missing foundational families. Do not silently count every platform spinner/progress style as a required component.
- **RefreshControl:** retained as controlled scroll-container attachment. Color/title/size/offset differences remain narrower contracts, not absence of pull-to-refresh.
- **DrawerLayoutAndroid:** navigation-adjacent; Neon navigation owns a drawer already. That is not full RN drawer-container parity and is not work for this audit.
- **Deprecated/unstable/internal exports:** SafeAreaView's useful inset ability is counted, not its obsolete platform asymmetry. ProgressBarAndroid, raw keyboard aliases, React Activity/VirtualView, renderer escape aliases, UIManager/bridge/TurboModules/JSI and dev tooling are not a requirement to import React/RN internals. Solid, Host, std and Ion are the owning seams where applicable.
- **Optional domains:** location, notifications, haptics, network info, storage, audio, camera and pickers must not inflate an RN-core coverage denominator. Their existing service modules were discovered, not exhaustively certified.

## Parent reconciliation and priorities

The parent rejected or narrowed these tempting conclusions:

1. **Native animation is not universally timer-based.** `createNativeHost` installs the frame driver; UIKit uses CADisplayLink, Android resolves Choreographer, with a timer fallback. See native host scheduleFrame and platform bridges. The default in frame.ms alone is insufficient evidence.
2. **The duration+17 LayoutAnimation timer alone is not a Neon-only parity defect.** `RN/Libraries/LayoutAnimation/LayoutAnimation.js` configureNext uses the same race timer, plus optional native completion. Keep the concrete missing delete/position/config behavior separate from a stronger completion contract neither timer proves.
3. **Empty unforkEvent alone is not failure for every RN input.** `RN/Libraries/Animated/AnimatedImplementation.js` unforkEventImpl also does nothing for ordinary functions; it detaches only AnimatedEvent objects. Neon lacks that richer detachable/native-event representation, rather than breaking every plain-function fork case.
4. **Reduced-motion integration is not a wholly missing ability.** Preference APIs and configurable animation durations already permit author policy. Automatic helper integration is an additional policy/lifetime concern; copying Flutter defaults is not assumed.
5. **Missing names are not missing mechanisms.** Style/composition covers many Flutter boxes; ImageLoader covers size/prefetch; Solid covers derived values/command composition; Yoga has RTL support beneath the unexposed Neon seam; Void owns drawing. Direct imports are not absent implementations.
6. **Absent editing metadata is not proof all IME/autofill/selection fails.** OS/browser controls retain built-in behavior. Richer portable control and documented ignored paths are the finding.
7. **Source plausibility is not runtime certification.** In particular, native custom accessibility activation, animation cleanup consequences, Unicode/grapheme/selection cases, default-value updates, image stress and advanced hit testing still require their real consumers.

Recommended order, if implementation is later authorized:

1. Make secure-input and alternate activation/key-delivery contracts visible with runnable host regressions; fix or explicitly reject unsupported paths.
2. Close the shared focus, pointer/hit-test and accessibility action/state boundaries needed to build accessible custom controls.
3. Complete editing/autofill/text/RTL/typography, image-source/memory and keyboard/scroll contracts for real app workflows; eliminate misleading accepted no-ops.
4. Resolve animation lifetime/config holes on the existing model. Evaluate Flutter-only advanced layout/scheduler/drawing/system opportunities separately; no public animation replacement, Flutter renderer or RN bridge/worklet engine is approved by this audit.

Uninspected remainder includes a full inherited-prop/native-schema denominator; every optional service; std/Ion ABI and asset/orientation/embedding surfaces; Flutter engine dart:ui implementation; all SVG filter/format contracts; dynamic platform colors; assistive-technology, hardware keyboard, autofill-provider and Unicode edge cases. The earlier name-coverage milestone and scoped measurement tests cannot establish universal RN/Flutter parity or a defensible coverage percentage.
