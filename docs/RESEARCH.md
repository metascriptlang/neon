# Programmable distributed database — research

Research in progress, started 2026-10-19. This file owns the reference survey, external source anchors, rejected paths, measurements and remaining evidence gaps. It is not implementation approval or a claim that a database has been selected.

The approved product/database requirements and proposed author contract are in [borderlessRuntimeDesign.md](borderlessRuntimeDesign.md#required-database-capabilities). Its existing source ledger and reproducibility section retain the earlier investigation; this survey extends them rather than duplicating them.

Current conclusion: no inspected engine/composition has passed the complete contract. Keep FoundationDB/Record Layer as transactional-authority references and Jazz/Groove as reusable non-SQL client/query/storage leads, **not a proven combined stack**. Badger's tested bare-KV predicates fail two cardinality workloads; Jazz's default fresh-account abrupt restart fails twice even though established-identity browser recovery/replay passes. Neither limitation may be hidden by a weaker adapter contract.

## Evidence scope

- **Discovery:** a candidate or search result, not yet verified against primary material.
- **Docs:** primary documentation read; implementation and performance remain unverified.
- **Source:** named paths/symbols inspected at a pinned revision; not a whole-project correctness or security audit.
- **Probe:** a bounded runnable check, with exact artifact/version/tree, command, output and limits.
- **Integration:** the actual production boundary/consumer exercised. No new platform integration is established by the survey so far.

A query builder, scalar UDF, stored procedure, general query program and distributed dataflow are different execution models. Likewise, replication, multiple independent databases, distributed storage and partitioned writes within one database are different scaling claims. The survey keeps these distinctions explicit.

## Primary-documentation and partial-source observations

### Rama — Docs, not an engine inspection

Primary pages read: [PStates](https://redplanetlabs.com/docs/~/pstates.html), [query topologies](https://redplanetlabs.com/docs/~/query.html), [ACID semantics](https://redplanetlabs.com/docs/~/acid.html), retrieved 2026-10-19. These are unpinned live documentation, not independently measured guarantees.

- PStates distinguish an internal, in-progress/unreplicated view from an external, replicated/durable view. Visibility is part of the transaction boundary, not synonymous with executing an update.
- Streaming atomicity covers an event on one partition; a partitioner starts another event. Microbatching publishes changes across the topology's partitions together. These are different mechanisms, not a blanket claim of globally serializable arbitrary transactions.
- The documented isolation depends on access context: own-topology state, another topology in the same module, or a different module. Cross-module reads are described as similar to read committed. A module/task placement decision therefore affects semantics, not only speed.
- Query topologies are predefined, on-demand distributed computations using the dataflow API. They can combine multiple PStates/tasks. This is valuable partitioning/query-placement prior art, but not proof that an arbitrary ordinary MetaScript function is automatically planned or distributed.
- Core-engine source/license eligibility and independent runtime behavior remain unestablished here. Free downloads, Java examples and the separate `agent-o-rama` project's license do not establish an open-source Rama core.

### Convex — Docs plus one source seam

The [official overview](https://docs.convex.dev/understanding/overview), retrieved 2026-10-19, makes its programming model unusually relevant: pure read queries, whole-function mutation transactions, automatic conflict retries and subscription reruns driven by read dependencies. Queries/mutations disallow nondeterministic operations such as network requests. The same page says cloud persistence uses PlanetScale/MySQL and self-hosted options use SQLite, Postgres or MySQL. Therefore this is programming-model prior art, not an acceptable SQL-free foundation as documented; its current FSL grant is a separate concern.

At `95d8719cb6931cd2322453bb900dfcd5a732fe81`, [`crates/database/src/reads.rs`, `ReadSet::writes_overlap_by_index`](https://github.com/get-convex/convex-backend/blob/95d8719cb6931cd2322453bb900dfcd5a732fe81/crates/database/src/reads.rs#L164-L220) tests writes in a timestamp window against index-read intervals and separately tracks search dependencies. This is stronger evidence than assuming only the returned record IDs are dependencies. Admission, guest execution, commit validation, persistence and subscription cutover have not yet been traced end to end in this expanded pass.

The overview also describes a client mutation queue **in memory**. That statement does not establish an autonomous durable offline client database.

### SurrealDB — distinguish JavaScript scripting from the Wasm extension path

At `18971ffba781a796c0ad3897bb4b82432c241e4c`, two distinct source paths are visible:

- [`surrealdb/core/src/fnc/script/main.rs`, `run`](https://github.com/surrealdb/surrealdb/blob/18971ffba781a796c0ad3897bb4b82432c241e4c/surrealdb/core/src/fnc/script/main.rs#L44-L119) constructs a QuickJS runtime with configurable stack/memory/time limits and cancellation, then exposes the current query context. [`modules/surrealdb/query/mod.rs`, `query`](https://github.com/surrealdb/surrealdb/blob/18971ffba781a796c0ad3897bb4b82432c241e4c/surrealdb/core/src/fnc/script/modules/surrealdb/query/mod.rs#L47-L104) runs subqueries through that context and serializes pending subqueries sharing it. That local serialization is not evidence of a database-wide writer lock. The host also registers `fetch`; this is not by itself Convex-style deterministic mutation isolation.
- [`surrealism/runtime/src/config.rs`, `Target` and `AbiVersion`](https://github.com/surrealdb/surrealdb/blob/18971ffba781a796c0ad3897bb4b82432c241e4c/surrealism/runtime/src/config.rs#L7-L34) belongs to a separate Wasm extension runtime. Its declared build target is Rust; the current ABI constant is 2. [`host.rs`, `implement_host_functions`](https://github.com/surrealdb/surrealdb/blob/18971ffba781a796c0ad3897bb4b82432c241e4c/surrealism/runtime/src/host.rs#L144-L197) registers typed-byte host calls through Wasmtime's component linker. The core implementation, [`surrealdb/core/src/surrealism/host.rs`, `Host::sql` and `Host::run`](https://github.com/surrealdb/surrealdb/blob/18971ffba781a796c0ad3897bb4b82432c241e4c/surrealdb/core/src/surrealism/host.rs#L143-L251), narrows module capabilities and evaluates through the current query context/options. Full commit/rollback linkage remains unverified; this is not demonstrated MetaScript guest support or a direct indexed-storage ABI.

The QuickJS bridge's [`create_query_data`](https://github.com/surrealdb/surrealdb/blob/18971ffba781a796c0ad3897bb4b82432c241e4c/surrealdb/core/src/fnc/script/main.rs#L17-L42) explicitly requires the runtime not to outlive borrowed query data. A reusable execution ABI must establish context lifetime, not merely expose a pointer. No memory-safety defect is asserted from this inspection. Root BSL restrictions remain independent of the mechanism's research value.

Two traps matter for the platform contract:

- **Context isolation is not heap reset.** [`runtime.rs`, `Runtime::acquire_controller` / `release_controller`](https://github.com/surrealdb/surrealdb/blob/18971ffba781a796c0ad3897bb4b82432c241e4c/surrealism/runtime/src/runtime.rs#L281-L351) reuses Wasm linear memory/statics while replacing or clearing host invocation context; trapped instances are to be discarded. [`controller.rs`, `Controller::set_context` / `clear_context`](https://github.com/surrealdb/surrealdb/blob/18971ffba781a796c0ad3897bb4b82432c241e4c/surrealism/runtime/src/controller.rs#L101-L120) confirms what gets replaced. Caller/auth boundaries, mutable guest state, rollback and deterministic replay therefore need separate verification. This observation is not a demonstrated cross-user security defect.
- **A host import named KV need not be durable database storage.** [`kv.rs`, `BTreeMapStore`](https://github.com/surrealdb/surrealdb/blob/18971ffba781a796c0ad3897bb4b82432c241e4c/surrealism/runtime/src/kv.rs#L1-L58) is explicitly process-memory-only and disappears on restart, cache eviction or runtime drop. The read-only inspection of [`tests/surrealism_integration.rs`, `check_persistent_state`](https://github.com/surrealdb/surrealdb/blob/18971ffba781a796c0ad3897bb4b82432c241e4c/tests/surrealism_integration.rs#L410-L442) checks repeated calls, not process-restart durability; it was **not run** here. Application DB access through `sql`/`run` must not be conflated with that volatile module store.

[`runtime.rs`, `Runtime::new`](https://github.com/surrealdb/surrealdb/blob/18971ffba781a796c0ad3897bb4b82432c241e4c/surrealism/runtime/src/runtime.rs#L147-L176) combines optional server/module limits, taking the smaller when both exist. [`create_controller`](https://github.com/surrealdb/surrealdb/blob/18971ffba781a796c0ad3897bb4b82432c241e4c/surrealism/runtime/src/runtime.rs#L393-L437) installs the optional memory limiter and epoch deadline. The presence of these hooks does not prove a safely bounded default profile or accounting for all host/reentrant work. Those remain probe/audit questions.

### RethinkDB — Docs establish a server-side JS expression, not the whole DB-program contract

The [primary `r.js` reference](https://rethinkdb.com/api/javascript/js/), retrieved 2026-10-19, demonstrates JavaScript expressions and row predicates executing on the server, with a documented default timeout of five seconds. It recommends native ReQL operators when possible. This page does not establish arbitrary guest code with indexed DB host calls, whole-function transaction semantics, partitioned write scaling or a MetaScript execution path. Retain the distinction between a server-side expression/UDF and an application program inside a transactional DB; do not infer either stronger support or complete absence from this page alone.

### FoundationDB — source-backed range conflicts and commit stages, not a new cluster result

[`commitproxy/CommitProxyServer.cpp`, `determineCommittedTransactions`](https://github.com/apple/foundationdb/blob/487620d5aa41152b1f034f4e932005a87eb2947f/fdbserver/commitproxy/CommitProxyServer.cpp#L1149-L1167) combines the participating resolvers' decisions. The [commit-stage sequence](https://github.com/apple/foundationdb/blob/487620d5aa41152b1f034f4e932005a87eb2947f/fdbserver/commitproxy/CommitProxyServer.cpp#L2176-L2195) waits for resolution/post-resolution, then [`transactionLogging`](https://github.com/apple/foundationdb/blob/487620d5aa41152b1f034f4e932005a87eb2947f/fdbserver/commitproxy/CommitProxyServer.cpp#L1890-L1910), then replies. The logging wait races its log-push future against evidence of a later committed version. This is a source trace of coordination/acknowledgement boundaries, not an independently verified log-quorum, crash-recovery or throughput guarantee.

Two important ceilings remain:

- The pinned [developer guide, long-running transactions](https://github.com/apple/foundationdb/blob/487620d5aa41152b1f034f4e932005a87eb2947f/documentation/sphinx/source/developer-guide.rst#L485-L513) describes a roughly five-second transaction limit and distinguishes per-entity decomposition from globally consistent version indirection. Do not silently split an atomic application action into multiple transactions to get around it. Whether a chosen runtime's workload fits this limit remains an acceptance question.
- A retry loop is not command deduplication. The pinned [unknown-result guidance](https://github.com/apple/foundationdb/blob/487620d5aa41152b1f034f4e932005a87eb2947f/documentation/sphinx/source/developer-guide.rst#L566-L598) warns that retrying `commit_unknown_result` can repeat an effect. [Automatic idempotency](https://github.com/apple/foundationdb/blob/487620d5aa41152b1f034f4e932005a87eb2947f/documentation/sphinx/source/automatic-idempotency.rst) exists, so it must not be overlooked; this revision labels it experimental/not production-recommended and still documents ambiguous `transaction_timed_out` / `cluster_version_changed` outcomes. It is not evidence that the platform's durable command/outcome lifecycle is solved.

No `fdbcli`, `fdbserver` or Docker command was found on PATH in this environment check. No installation or cluster launch was attempted, and no new FoundationDB test was run.

### Record Layer — uniqueness consumes the range contract; a continuation does not pin a snapshot

A future prototype must select and prove these boundaries together. An ordered-KV trait or a module loader is not permission to assume the rest, and no platform/compiler/runtime implementation is approved by this research record.

The next acceptance boundaries are concrete, not a request to assemble every surveyed project:

- A local-durable acknowledgement must retain enough identity/namespace/key/schema metadata to reopen the acknowledged data and pending intent after immediate process termination, **including the first account's first session**. Normal close, a waiting period or manual account recovery cannot stand in for this gate.
- The authoritative storage transaction must protect the read predicates used by application invariants and atomically persist data, index changes and command outcome. A KV batch or snapshot alone does not pass; the Badger controls discriminate these cases.
- Real MetaScript guest execution must share that transaction and enforce host capabilities, deterministic retry behavior, deadline/fuel/heap bounds and fail-closed authorization. The surveyed VM/ABI sources are references, not an existing MetaScript integration.
- The authority/client composition must demonstrate rejected prediction/rebase, duplicate and ambiguous-command outcomes, authorization revocation, artifact/schema compatibility and persistent restart on actual native/browser consumers.
- Partitioned write and query work must operate within one logical database and survive leader/migration/rebalance failures. Shared roots, read replicas, independently routed apps and a single-Core loopback probe do not satisfy this gate.

Recommendation at this checkpoint: reuse the proven mechanisms by layer, keep the failing contracts explicit, and do not choose a complete engine or promise a thin FoundationDB-to-Groove adapter. The source-backed compatibility constraints below identify why integration is not yet established. Building that integration, a new backend, or a requirement that app authors compensate for these limits needs separate approval.
